## ADDED Requirements

### Requirement: Canonical client-neutral mission

The system SHALL define Escapement's canonical mission as converting available agent capacity plus delegated authority into verified, delivered outcomes while reserving human attention for consequential choices. The canonical mission SHALL NOT depend on the name or continued use of any client, planning tool, task store, source-control host, or policy engine.

#### Scenario: Current tool is replaced

- **WHEN** a current client, planning tool, task store, or source-control adapter is replaced
- **THEN** the canonical mission remains valid without modification

#### Scenario: Host-specific identity is proposed

- **WHEN** an identity-bearing surface defines Escapement in terms of Claude Code, Codex, Pi, OpenSpec, Beads, GitHub, OPA, or Cedar
- **THEN** the identity consistency check rejects that definition

### Requirement: Durable capability chain

The system SHALL identify intent and authority, design and specification, executable work breakdown, capacity allocation, isolated execution, action-local continuation, independent outcome verification, authorized landing, and learning as durable Escapement capabilities.

#### Scenario: Design and work breakdown remain core

- **WHEN** the canonical capability model is rendered or documented
- **THEN** design/specification and executable dependency-aware work breakdown are present as first-class capabilities rather than optional tool ceremonies

### Requirement: Current tools are replaceable adapters

The system SHALL document current tools as implementations of durable capabilities and SHALL permit explicit adapter sections to name those tools without making them part of the core definition.

#### Scenario: Adapter mapping names current tools

- **WHEN** a current-integration section maps OpenSpec, Beads, Git worktrees, agent clients, or GitHub to durable capabilities
- **THEN** the narrative consistency check accepts the tool-specific mapping

#### Scenario: Tool name enters core mission

- **WHEN** a current tool name appears in the canonical mission or core product definition
- **THEN** the narrative consistency check fails

### Requirement: Mission and operating doctrines have distinct roles

The system SHALL use mission command and leverage to define why Escapement exists, closed-loop control to define how it operates, flow and constraint measures to evaluate it, and enabling-bureaucracy principles to evaluate gates.

#### Scenario: Gate doctrine replaces the mission

- **WHEN** a surface describes gates, policy, or compliance as Escapement's primary outcome
- **THEN** the surface fails identity review unless it also anchors the gate to verified delivery and consequential human attention
